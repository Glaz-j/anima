# Minecraft 小型技能考场

目的：分别验证身体技能能否完成任务、规划与即时操控能否在世界持续运行时协作。考场只使用 `var/minecraft/skill-exam/server` 的独立存档，游戏端口 `25575`、RCON 端口 `25585`；不连接或重置 `25565` 的持续生存世界。

这是一套基础设施和一期题库。**单元测试通过、参考控制器通过、pi Agent 通过，是三种不同证据。** 不把 fixture 回放、未实现技能或单次成功记作系统已稳定。

## 运行

从 Anima 根目录运行。使用仓库锁定的 Mineflayer 和已安装 Minecraft Java 1.21.4；无需新增框架。`minecraft:exam` 是 `adapters/minecraft/benchmark/cli.ts` 的 npm 入口；下方直接写脚本也能运行。

```powershell
# 查看一期题目和二阶段设计 gate
node adapters/minecraft/benchmark/cli.ts list

# 仅创建独立目录和配置，不启动，也不会接受新的 EULA
# 要求本项目原有 Minecraft runtime 已接受 EULA
node adapters/minecraft/benchmark/cli.ts prepare

# 在单独终端启动考场；如果该端口的考场已运行，不重复启动
node adapters/minecraft/benchmark/cli.ts serve

# 另一个终端，先测试真实身体技能
node --env-file-if-exists=.env adapters/minecraft/benchmark/cli.ts run --task gather-01 --mode skill --architecture dual

# 运行全部一期题；每次场景会重置，Minecraft 世界在计分期间从不停时
node --env-file-if-exists=.env adapters/minecraft/benchmark/cli.ts run --task all --mode skill --repeat 5

# 让 pi 自行规划，不能将参考计划的成绩当作这一步的成绩
node --env-file-if-exists=.env adapters/minecraft/benchmark/cli.ts run --task interrupt-resume-01 --mode agent --architecture dual --delay 10000

# 列出已有成绩，不启动游戏或模型
node adapters/minecraft/benchmark/cli.ts report

# 验证裁判、通信和指标逻辑；fixture 明确排除在真实成绩外
node --test tests/skill-exam.test.ts tests/skill-exam-metrics.test.ts
```

`--task` 支持逗号分隔，例如 `gather-01,craft-01`。`--repeat` 范围 1–100。`--delay` 与 `--model-delay-ms` 等价，单位毫秒，范围 0–60000。额外延迟由 executor 在模型请求路径实现；默认参考技能模式没有模型请求，给它设置延迟不能证明模型等待期间的鲁棒性。

`--architecture` 默认 `dual`，在保持同一技能库的前提下选择三种候选执行架构：

| 架构 | 规划与身体的关系 | 快速反应 |
| --- | --- | --- |
| `serial` | 规划提交目标后等待完成或首次技能失败，再继续决定 | 不启用 |
| `parallel` | 异步提交目标，持续技能独立执行 | 不启用 |
| `dual` | 异步规划与持续技能并行 | 只启用目标明确授权的反应 |

CLI 把架构传给候选工厂并记入每轮结果，实际行为由 executor 实现；标签本身不是该架构有效的证明。比较时分别运行三个架构，保持模式、模型、题目版本、延迟和源码版本相同。`report --mode agent --architecture dual` 可以只查看某组。

默认 agent 接入已经在 `runTask` 层实现三种模式：serial 的 `body_plan` 等待该目标完成、首次技能失败、到期或被替换；收到本次目标的失败/取消回执时，撤销剩余步骤并等待自己的执行收尾，再把真实失败交回规划，避免让普通 ReAct 对照也被迫等待错误动作重试到租期结束。旧目标的回执不结束新目标的等待，旧规划的取消不能停止外部新目标。parallel/dual 的提交立即返回。serial 和 parallel 会强制移除请求中的 reactions，不能靠模型额外授权绕过对照条件。`--delay` 逐次施加在逻辑模型请求上，工具回执后的下一次请求也会等待；本地技能继续独立运行。`modelCalls` 统计该逻辑请求入口，不是底层 HTTP 重试次数；`modelWaitMs` 包含注入延迟和模型流式回复等待。

三架构的效果比较应使用 **agent 模式**。当前 skill 参考战斗计划通过空步骤加应急授权选择目标；禁用反应的 serial/parallel 在该题没有等价的显式攻击参考计划。因此 CLI 拒绝 skill 模式搭配非 dual 架构，避免把无攻击计划导致的失败解释为串行规划能力差。skill 模式主要验证明确参考计划与技能执行是否可达。

每次 trial（包括同一个 CLI 的 `--repeat`）重新创建候选的 Mineflayer 连接、身体控制器与私有记忆命名空间。上一轮完全停止并断开后，下一轮才进入初始化，避免上轮停止锁存、完成进度或历史对话改变下一轮的初始条件。

默认 executor 是 `benchmark/body-executor.ts`。可使用 `--executor <模块路径>` 接入其他候选系统。CLI 传给候选模块的只有公开游戏连接信息，不传 RCON 密钥、题库布局、隐藏扰动或裁判证据。

RCON 凭据只保存在本地考场配置文件中，不输出到控制台或结果。`serve` 只启动它自己持有的独立 Java 进程；Ctrl+C 请求该进程保存并停止。

## 一期题目与判分

| 题目 ID | 公开目标 | 裁判必要证据 |
| --- | --- | --- |
| `combat-single-01` | 持铁剑战胜一只成年僵尸 | 开题时目标活着；目标随后死亡；本玩家对应击杀统计增加；玩家存活 |
| `combat-multiple-01` | 战胜两只成年僵尸 | 两只目标均不存在活体，并有两次服务器玩家击杀统计 |
| `parkour-empty-01` | 空手依次跨越两段缺口 | 依序落稳在两平台、跳跃统计增加至少 2；没有获得物品；没有圆石放置 |
| `parkour-items-01` | 用最多 8 块圆石搭桥、登上高台 | 依序抵达检查点，真实放置至少一块、最多 8 块，最终落稳 |
| `craft-01` | 从三根原木合成木镐 | 木镐合成统计增加，且新木镐实际进入背包 |
| `gather-01` | 采集并拾取六根原木 | 六次原木挖掘统计及背包净增加六根原木 |
| `navigate-01` | 绕过基岩墙依次抵达两个位置 | 服务器位置按顺序进入两个区域，不要求额外停留 |
| `water-rescue-01` | 从水池浮起并上岸 | 最终抵达指定干燥岸上，落地且存活 |
| `eat-resume-01` | 进食后继续采集 | 初始饥饿已由服务器验证；吃牛肉统计、食物减少、饥饿值提高，然后采集继续增加 |
| `interrupt-resume-01` | 采集途中遇敌，击败后继续 | 已有实际采集进度后注入敌人；观察到活体；真实击杀；击杀后又有新的原木入包，最终达到总数 |

空手跑酷和材料跑酷有五格高的基岩侧墙，防止绕过缺口走外侧平地。方块预算、平台和目标是公开任务条件；注入敌人的具体时点只由考场控制。所有题目死亡或离开允许空间都会失败。跑酷和上岸的“落稳”要求位置与落地条件在两次以上服务器观察中持续至少 250ms，导航只要求抵达。

初始化期间允许裁判建场、清空背包、补满生命、给予题目规定物品，并临时使用创造模式防止建场坠落。**所有这些动作都在开题前完成；开题前恢复生存模式、清除效果，再记录初始真值。** 饥饿题用原生饥饿效果消耗饱和度和食物，每 250ms 读取玩家 NBT，直到 food≤12 立即清除效果；最长 12 秒，生命下降则拒绝本轮基线。不使用固定等待假定已经饿了，不修改玩家 NBT。

计分期间世界按 20 TPS 目标持续运行，敌人有正常 AI；不暂停来等待模型，也不给机器人持续无敌、无限物品、传送或治疗。开题敌人先以 `NoAI` 状态创建，完整初始采样并验证玩家满血后立即激活；初始时间戳保留，另记 `opponentsActivatedAt`，激活到候选开始行动期间的暴露与伤害也计入成绩。除题目声明的敌人注入外，裁判不帮助候选执行任务。

## 证据与隔离

`VanillaExamAdapter` 从独立服务器读取玩家 NBT（位置、生命、饥饿、空气、背包）、服务器统计 scoreboard、目标实体状态和 `gametime`。战斗场景禁用自然刷怪，初始化清除旧非玩家实体，并要求只有考生在线。因此指定数量的目标消失必须同时有对应玩家击杀统计，不能把卸载、清除或敌人自己消失算胜利。

输入命令、LLM 自述、客户端“已调用工具”等都不能直接满足成功条件。挖掉方块但未拾取、发送合成但没有产物、对空气挥剑，都不算完成。

`SkillExamReferee` 是独立的确定性裁判。候选只能通过自己的 Mineflayer 感知行动。`ExamExecutor.start()` 只收到公开说明、actor、mode、延迟和遥测回调；agent 模式连技能类别也不接收。公开说明中的坐标是任务目标，不是隐藏路线。

RCON 的命令响应可能分帧；客户端收齐响应后才进入下一命令。为了适应 Vanilla 的请求读取方式，响应终止屏障须在收到本请求首个响应后才发送，避免两个请求被 TCP 合并后导致断开。RCON 仅用于考场管理和裁判，不开放成 NPC 工具。

每次运行保存到 `var/minecraft/skill-exam/results/exam-<UUID>/`：

- `task.json`：完整题目快照与版本，只供考场复核。
- `evidence.jsonl`：实际服务器证据快照。
- `events.jsonl`：候选控制事件与模型调用事件。
- `referee.jsonl`：隐藏扰动实施时间。
- `result.json`：状态、原因、指标和是否属于真实成绩。

结果 schema 2 还记录 `architecture`、固定 `taskRevision`、`candidate.model`（provider/id）、可选 controller 标识，以及 `source.gitHead/dirty/workingTreeId`。CLI 在导入候选模块前采集一次源码身份；workingTreeId 是已跟踪修改和未跟踪源码内容的短哈希，不保存 diff、源码正文或密钥。它标识启动时工作区，不替代干净 commit 的完整可复现性。候选提供的 metadata 只按白名单保留模型与控制器名称；HTTP 配置、API key 等额外字段不会进入结果。

旧 schema 1 缺架构归因的结果保留为 `unattributed`，不猜测它们属于 dual，不纳入新架构 gate。无模型身份的 agent 结果或无源码身份的结果也不能满足 gate。

错误必须保留原始原因，停止或清理失败追加说明。超时计失败；能力缺失计 `unsupported`；断线、裁判证据缺失、停止不确认或服务器明显停时计 `infra-error`；人工取消计 `cancelled`。fixture 运行即使逻辑满足，`realScore` 也始终为 `false`。

候选确认模型提供商或连接基础设施不可用时，应调用 `context.fail('不含凭据的错误摘要')`。runner 立即中断、停止身体并记 `infra-error`，不能把持续 Connection error 后的超时当成 Agent 能力失败，也不持续重试制造无效请求。正常的寻路、合成、战斗失败不能用这个接口排除出成绩。

## 指标

首先报告成功率、完成耗时、受伤量、死亡次数。不同任务、题目版本、模式和延迟条件应分别比较，不用混合总分掩盖薄弱项。

输入指标统计**实际发给控制器的输入变更与离散操作**。持续按住前进被重复写 100 次只算一次；攻击/使用物品的离散请求逐次计数。20 Hz 控制检查不是 1200 APM。输入 APM 也不代表服务器接受或该动作有用，必须和任务结果、实际伤害、采集成果一起看。`effectiveInputs`/`effectiveApm` 保留为兼容字段，`issuedInputs`/`issuedInputApm` 与 `inputMetricScope` 明确口径。

快速反应延迟从 NPC 自己的 `hazard-observed` 到同一 `hazardId` 的 `reaction` 遥测事件计算，附样本数与未响应数；缺遥测不显示为零延迟。RCON 约 200ms 的裁判快照不是精密反应计时器。

跨架构比较反应速度还要求同一危险定义、相同的本地观察起点，以及对手动计划技能和自动反应相同的输入关联规则。历史实现曾只在授权自动浮水时报告水中危险，并只把自动反应归为响应；这类结果不能用于 serial/parallel/dual 的反应延迟对比。没有 hazard 样本表示缺少该项证据，不表示没有危险或反应即时。

默认 executor 现使用独立的 `ExamReactionObserver`（事件标记 `observer-v2`）：它只读考生本地可见状态，无论有没有授权自保都会观察淹水与7格内可见敌人；多敌视为一个持续危险事件，1秒消失宽限避免可见性闪烁重复计数。每50ms观察一次，也在真实输入发出时补采本地状态，避免漏掉早于定时器的首次响应。零延迟表示响应落在该观察分辨率内，不是零物理延迟。浮水/跳起、combat/retreat/attack/shoot 的相关实际输入可登记响应，手动和自动技能使用同一规则。单独 move/travel 等行动的意图无法从输入证明，因此未登记响应只能解释为“未观察到已定义应对输入”，最终效果仍看生存、伤害与服务器目标判据。

控制检查间隔报告 P95、最大值及观察窗口首尾空档。空档可能来自合理待机，不能单凭一个 gap 自动判行为失败。模型请求数和等待时间帮助区分身体持续执行与模型速度。

服务器真实时间比例定义为 `经过游戏 tick × 50ms / 墙钟经过时间`。运行满五秒后低于 0.65 的场次标记基础设施异常，不拿低 TPS 或暂停产生的优势算正常实时成绩。该阈值是初始健康检查，并非游戏运行完全流畅的证明。

## 候选接口

```ts
export async function createExamExecutor({ root, host, port, version, actor, architecture, mode }) {
  return {
    metadata: { model: { provider: '实际提供商名称', id: '实际模型ID' }, controller: '控制器版本' },
    executor: {
      async start({ instruction, category, mode, architecture, modelDelayMs, signal, emit, fail }) {
        // 提交有效目标后及时返回。完整身体任务在独立生命周期中继续。
        // 不将 start() 本身阻塞在采集、LLM 回复或任务完成上。
        return { async stop() { /* 确认所有动作已停止并释放身体 */ } };
      }
    },
    async close() { /* 退出考生连接，释放本模块资源 */ }
  };
}
```

启动接口三秒未返回、停止接口五秒未确认均属于基础设施问题。收到 `AbortSignal` 后必须主动取消；迟到的启动结果也会被要求停止。除候选自身的遥测外，`runSkillExam` 不接受候选提交“成功”来替代裁判。

## 优化与二阶段

失败纠正可另运行 `node --env-file-if-exists=.env adapters/minecraft/benchmark/replan-probe.ts --run --delay=10000`。该诊断在同一独立考场由夹具注入一个错误站位，确认工作挂起后不自动重试，再让真实 pi 根据自身观察重新规划，到达公开目标由服务器位置判定；记录失败次数、模型等待重叠、纠正延迟与单身体所有者。初始错误由夹具注入，不能称为模型自主产生的失败，也不计入一期成绩。输出在 `var/minecraft/skill-exam/replanning/`；运行时考场必须没有其他考生。

首轮用 `skill` 模式逐个定位动作可达性；随后测试 `agent` 模式，再做 0、2、10、20 秒额外模型延迟的对照。保持模型、公开目标、物品和题目版本一致；统计失败，不挑最佳一局。跑酷课程还需要实际参考控制器的通过证据，几何看起来可行不等于已验证。

汇总先按 mode、architecture、模型、控制器、源码身份和模型延迟分组；每组仍显示各题目的独立 revision。当前自动一期 gate 要求同一组内每道当前版本题至少 5 次有效、带输入/控制遥测的零额外延迟实测，每道成功率至少 80%。跨架构、模式、模型、源码或旧题目版本的次数不能拼起来凑通过。

skill 组可以满足自己的 `phaseOnePassed`，但**50 次 skill 通过不能代替 agent 规划成绩**。只有 agent 组能获得该组的 `phaseTwoEligible`，总摘要的同名字段专指 dual agent 组。这只是进入二阶段的必要条件；还要人工审阅控制冲突、旧目标恢复、模型控制权及 agent 延迟矩阵，不能仅凭布尔 gate 宣称架构完成。

当前 gate 只检查任务成功率、次数、归因和基本输入/控制遥测存在，不检验反应延迟上限、未响应危险比例、输入是否有效或完整的延迟对照矩阵。`uninstrumented` 目前也可能表示整轮没有实际输入，而不仅是未安装遥测；这类场次要保留失败和具体原因，不能随意排除来提高成功率。80% 的门槛与每题五次是初步工程门槛，不是统计显著性的证明。

正式对照批次开始前应冻结实现和题目版本。文档或其他被追踪文件的修改也会改变现有 `workingTreeId`，因此调试期间产生的不同源码组不能拼接通过 gate；忽略目录中的模型配置、人格数据、代理上游模型版本等尚未全部指纹化，同一源码哈希也不是实验环境完全一致的证明。每轮还须隔离记忆、事件和身体状态，确保第一轮与后续轮拥有相同的初始授权条件，不能把上轮 stop 的残留锁存带入下一场。

### 二阶段可复现任务规格（尚未实现）

以下六项与 `tasks.ts` 的 `STAGE_TWO_PLAN` 一一对应，全部标为 `design-only`，没有注册成可运行题目。`--task all` 仍只运行原有一期十题。首次实现应先用独立参考控制器证明场景物理可达，再进行 Agent 测试；参考编排不进入 Agent 提示、工具回执或私有记忆。

六项共同要求：每个实例保存完整 manifest（方块、实体、物品、出生点、公开目标、扰动触发规则、超时、Minecraft/依赖/模型/源码版本）及哈希；固定世界种子还不足以固定怪物行为，因此重复时重建实例并公开全部结果。正常难度、真实持续 tick，开题后不暂停、不治疗、不增发材料；第 5 项仅允许事先声明的一次死亡注入。保留 `failed/unsupported/infra-error` 区分，缺失服务器证据不能补成成功。

#### 1. 近远程混合敌人与掩体

- **编号与主测层：** `stage2-combat-mixed-01`；快速战斗、局部导航及大脑选择目标。时限 150 秒。
- **初始条件：** 32×32 封闭夜间场地，满血饱食，铁剑 1、皮革胸甲 1，无食物和建材；一只成年僵尸、一只持弓骷髅，固定基岩掩体。具体实体坐标、朝向、装备耐久和掩体体素写入实例 manifest；完整基线采样后激活敌人。
- **成功／失败证据：** 两个指定目标先被服务器观测为活体、随后死亡，并分别增加本玩家的僵尸及骷髅击杀统计，玩家仍存活且未出界。死亡、超时、出界或外部补给失败；敌人互杀、卸载或消失不能代替玩家击杀。真实损血、箭矢命中、进入掩体与换目标时序单独报告，掩体使用不是额外的强制通关答案。
- **隔离与泛化：** 仅一名考生，禁自然刷怪和其他掉落来源。开发实例固定；留出实例使用整场旋转／镜像、交换敌人方向、经参考实测可达的掩体间距。Agent 只观察当前可见实体，不知道裁判的隐藏实体状态。

#### 2. 有限装备退守后恢复采集

- **编号与主测层：** `stage2-retreat-resume-01`；风险策略、应急接管、技能中断后的进度恢复。时限 180 秒。
- **初始条件：** 满血、服务器确认 food=12，木剑 1、木斧 1、熟牛肉 1，无护甲；六根原木与一个有掩体但不无敌的退守区。第一根原木真实入包后注入两只成年僵尸。公开目标明确要求遇险退守、进食、解决威胁并继续采集；具体注入时刻不提前告知。
- **成功／失败证据：** 敌人已出现且尚未全部解决时，服务器位置进入退守区并停留至少 250ms；进食统计增加、牛肉减少、food 提高。随后击杀两个指定敌人，且威胁解决后又有新原木入包，最终背包净增六根。死亡、超时、越界、缺少退守或战后恢复阶段、额外补给均失败。关闭自然回血；此题的“恢复”指工作恢复，不能要求裁判补满生命。
- **隔离与泛化：** 裁判不为考生关门、不拦截追敌，不透露追敌路径。留出实例交换退守方向、资源布局及敌人相对方位；物品预算变化必须公开并先证明可达，不能把不可解实例混入架构失败率。

#### 3. 转向连跳与有限材料

- **编号与主测层：** `stage2-parkour-turn-budget-01`；运动技能组合、空间规划、累计材料授权。时限 150 秒。
- **初始条件：** 满血饱食，仅四块圆石；从脚部坐标 `(0.5,64,0.5)` 出发，依次落稳于 `(3.5,64,0.5)`、`(3.5,64,3.5)`、`(7.5,64,3.5)`、`(7.5,65,5.5)`。检查点下为固定平台，之间有缺口、直角转向及一格登高；围挡防止外侧平地绕行。完整平台形状、围挡和失败平面必须在 manifest 中固定，以上仅是待参考实测确认的开发布局。
- **成功／失败证据：** 全部检查点按顺序落稳至少 250ms，玩家存活，真实跳跃统计至少增加 2，真实圆石放置至少 1 且累计不超过 4，方块与背包消耗吻合。原平台不可破坏；坠入失败平面、超时、错序绕行、超预算或外部掉落物补给失败。取消、续租、重试均不重置整题材料预算。
- **隔离与泛化：** 原始平台使用不可破坏材料，场内没有可挖材料来源。留出整场旋转／镜像与物理可达的间距、转向组合；开发后冻结的留出实例不进入调参。检查点属于公开目标，桥位和具体动作序列由 Agent 自行决定。

#### 4. 从容器取料、熔炼再制作

- **编号与主测层：** `stage2-furnace-container-01`；多步工序规划、库存确认、持续等待与容器交互。时限 180 秒。
- **初始条件：** 考生空背包；源箱恰有粗铁 3、煤炭 1、木棍 2，另有空熔炉、工作台、空目标箱各一个；设施坐标和朝向固定。场内没有铁锭、铁镐或可额外开采的矿物。公开目标为制作一把铁镐并存入目标箱。
- **成功／失败证据：** 服务器时序证明源箱扣料、炉内原矿转为铁锭及燃料消耗；玩家合成铁镐统计增加，目标箱真实新增铁镐 1。整题按源箱、熔炉、目标箱、背包和掉落实体维护守恒账，不能把预测背包当产物。死亡、超时、破坏设施、额外材料或错误成品失败；炉内转化／交付证据不足单列基础设施异常。首次实现需补齐可靠的熔炼和容器真值采集，不能只复用一期木镐计数器。
- **隔离与泛化：** 仅一个考生，裁判不快进熔炉、不替取产物、不填充目标箱。留出设施相对位置、朝向和距离；公开替换等价燃料时同步调整预算并验证可达。用同一个题目比较思考期间身体能否继续等待／执行，而非替某架构缩短真实熔炼时间。

#### 5. 死亡后新授权与迟到旧规划

- **编号与主测层：** `stage2-death-stale-plan-01`；大脑控制权、实体生命周期、版本校验与取消收尾。时限 120 秒。
- **初始条件：** 独立安全场地、固定复活点、`keepInventory=false`。原目标为移动；在其实际执行且一个基于旧观察版本的模型回复已被可信延迟器扣留时，runner 注入一次事先公开约定的真实死亡。使用正常重生流程，重生后等待新观察和显式授权；不把旧计划改写成新版本。
- **成功／失败证据：** 服务器死亡统计恰好增加 1，真实完成重生；释放旧回复后控制器拒绝旧版本，旧目标不恢复输入。大脑重新观察后显式提交新目标，身体接受并实际抵达，始终至多一个 native owner。第二次死亡、超时、接受旧版本、停止确认后旧技能重新发送动作、无新授权自动复活旧工作均失败。停止前已发出的动作可以在排空期间形成真实部分回执，不能把这些迟到确认误算为新发动作。
- **隔离与泛化：** 此题必须有独立裁判，不能直接套用一期“死亡即失败”。保存死亡／重生／取消确认／模型回复到达／授权版本／原生输入及服务器位置时间线。固定变体为 2／10／20 秒延迟、旧回复在重生前后到达，以及相同等待流程的人工 stop、TTL 到期。后两项不是新增死亡次数，也不能用无模型探针代替真实迟到回复测试。

#### 6. 两 NPC 资源交接与共同制作

- **编号与主测层：** `stage2-coop-handoff-01`；多脑协商、真实交接、私有记忆隔离及并行控制。时限 180 秒。
- **初始条件：** 只有 A／B 两个考生，满血饱食，相距八格且处于正常通信范围；A 持铁锭 3，B 持木棍 2，无其他资源；共享工作台、空交接箱、空目标箱。双方只收到共同的铁镐交付目标及自己实际可见的信息，不分发包含两人私有背包／计划的全局提示。
- **成功／失败证据：** 至少一次跨玩家物资流转真实发生，双方背包、交接箱或掉落实体的时序相互印证；其中一人的铁镐合成统计增加，最终目标箱新增铁镐 1。双方存活，总物品账守恒，同一物品不能被重复记为已交付或同时属于两人。任一死亡、超时、额外资源、重复记账或只有口头承诺没有实物交付失败。候选工具／上下文访问审计若发现越权读取另一人的私有记忆，作为隔离失败单列报告。
- **隔离与泛化：** 每人独立模型上下文、记忆命名空间、授权版本和身体；只有游戏内实际通信可传递私人信息，裁判全知账不进入任一模型。当前一期 adapter 强制单考生，协作需要未来单独实现多考生裁判，不能通过关闭现有检查冒充完成。留出变体交换资源持有者／出生方位、移动交接箱、允许真实丢弃拾取，以及只给其中一个模型增加 10 秒延迟。

### 二阶段执行顺序与报告

一期当前 Agent 组满足门槛后，优先实现第 1、3、4 项的单体组合能力，再做第 2、5 项的中断和控制权，最后做第 6 项协作。每项先记录参考执行器的真实可达证据，随后对冻结开发实例进行 Agent 重复测试，再独立运行未用于调参的留出实例；两类成功率分开报告。三架构共用技能、感知、物品、目标、失败回执语义与时限，只改变等待方式和应急授权；对照顺序轮换，并区分冷启动自保与任务执行中的中断反应。

除每题成功率、耗时、受伤、死亡、输入及延迟指标外，另报永久失败重试次数、首次失败到有效新计划的时间、材料浪费、停用／替换后的旧命令数、物品交接守恒与各 NPC 的控制空档。APM 和无模型控制隔离探针都不能替代 Agent 成绩。六项目前都没有真实成绩或自动二阶段通过阈值，不能将设计元数据解释成已完成关卡。

参考项目：[MineDojo](https://docs.minedojo.org/sections/core_api/sim.html)、[MCU](https://github.com/CraftJarvis/MCU)、[MineCollab](https://github.com/mindcraft-bots/mindcraft/blob/develop/minecollab.md)。我们借鉴任务参数化、基础/组合任务分层和协作测试方法；本考场没有直接复现这些项目的排行榜成绩。

## 四 NPC 控制隔离探针

`node adapters/minecraft/benchmark/multi-owner-probe.ts --run` 使用已有 marker 对应的独立 25575 考场；不加 `--run` 只打印说明，不连接。必须空场且运行中的服务器容量至少为 4；不要与技能或 agent 考试并行运行。可信 runner 建立四条安全平地通道，候选 World 仅得到普通游戏连接。

探针用四个随机命名角色验证同时真实移动、停止 A 并排空其执行器、拒绝 A 的旧版本回复、显式恢复和替换目标。B/C/D 必须保持原授权和服务器实际位移，每个角色最多一个 native owner。运行中发现其他玩家立即退出，不踢人、不杀玩家；清理只停止和断开本次自己的四个角色。

结果及服务器 NBT/输入事件保存在 `var/minecraft/skill-exam/multi-ownership/<timestamp>/`。各角色报告分阶段控制检查间隔；A 被有意停止时的空档不代表调度卡顿。此探针没有模型调用，也不验证记忆隔离或社交协作，不能作为技能成绩或真实模型延迟实验。
